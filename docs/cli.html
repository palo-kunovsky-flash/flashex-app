CLI reference

flashex controls the running app from a shell, a script or an agent's hook. Every command answers --help with its own usage, and a wrong argument shows that command's help. Agents that take tools rather than commands use flashex mcp.

Which app it talks to

  • Inside a Flashex terminal, FLASHEX_SOCKET names that window's socket and FLASHEX_PANE_ID the terminal. Commands target that terminal unless you pass --surface. A command never falls back to another Flashex.
  • Outside Flashex, the default socket: ~/Library/Application Support/flashex/flashex.sock on macOS; on Windows %LOCALAPPDATA%\flashex\flashex.sock; on Linux $XDG_RUNTIME_DIR/flashex/flashex.sock, else ~/.local/share/flashex/flashex.sock.
  • The socket is 0600 in a 0700 folder, so only you can connect. [api] enabled = false turns it off.

Ids. flashex list shows projects, tabs, panes and terminals with their numeric ids. A terminal's id is called a surface. -- ends the options, so text after it may start with -.

Exit codes

CodeMeaning
0Done.
1An error: bad arguments, an unknown id, a refused request (the message says why).
2Flashex is not running (no socket, or this window has its API turned off); for events, also when the app closed the stream.

Commands

flashex list [--json|--agents]

Lists projects, tabs, panes and their surfaces (terminals, editors, previews, browsers), each named as its pane tab shows it. * marks the active project and > the focused surface; an agent's state is shown in brackets, with its session: what Claude Code calls it (brain-8d, or the name /rename gave it) and its id. --agents lists only the terminals with an agent, one line each with the names --to takes. --json prints the API's answer as is.

flashex message --to NAME [--wait] TEXT

A message to the agent in terminal NAME (its name, its number, or its Claude Code session's name). It waits in that agent's box while the agent works and is typed at its prompt, never into the middle of its turn. When the turn the message started ends, the agent's reply comes back to the terminal that sent it, the same way, by itself: the sender need not ask again. --wait waits for the reply and prints it here, so an agent can hand out a task and go on with its result in one step. At most 20 messages an hour go from one terminal to another, so two agents cannot answer each other for ever.

zsh
❯ flashex message --to ui "Build the settings form; tell me the file"
Waiting in its box (message 3, 1 there): it goes in at its prompt.

flashex team status [--json]

Every terminal with an agent: its number, its name, its state (running, waiting, idle), whether it works on a message, and how many messages wait in its box. A lead agent reads this instead of each helper's whole terminal.

zsh
❯ flashex team status
#12   lead                     running
#14   ui                       running    on a message
#15   tests                    idle        · 1 waiting

flashex team list [--json]

The project's teams and chains (files in .flashex/teams, looked for from the folder you are in up) and the templates a new one starts from.

flashex team start NAME

Opens a team's agents in a new tab, one terminal each in one pane, the lead in front (the others are its pane's tabs). Each terminal is named after its member, runs in that member's worktree when it has one (made beside the project, on branch team/<team>/<member>), and its agent is told who it is, who the others are and how to message them: Claude Code through its SessionStart hook (again after a compaction), other agents as their first message. The team's rules go in .flashex/teams/NAME/rules.md, a role's in .flashex/teams/NAME/<role>.md.

flashex mcp

Flashex as an MCP server over stdio, for agents that take MCP tools rather than run commands: team_message (a message to a team's agent, its answer back by itself or awaited), team_status, chain_next, list_agents and artifacts. The terminal it runs in is the sender. Add it to Claude Code with claude mcp add flashex -- flashex mcp.

flashex chain next [--block NAME] [TEXT]

In a started chain, hands the answer of the block it runs in (its newest one, or TEXT) on to the next block, or to block NAME (back to an earlier one with notes, say). The next block gets it at its prompt, headed with where it comes from and its own task, and is shown. Run it yourself when a block's result is ready, or tell the agent to (it calls the same command).

flashex team new TEMPLATE [NAME]

Writes a team file from a template into .flashex/teams (flashex team list names them): change its members, their agents and tasks there, then start it.

zsh
❯ flashex team new lead-builder-reviewer feature-x
/Users/you/code/app/.flashex/teams/feature-x.toml
❯ flashex team start feature-x
Started feature-x: 3 terminals, the lead in front.

flashex artifacts [--json]

The pages Claude published as artifacts, newest first: each one's title, its claude.ai link, the Claude account it belongs to (a page is readable and updatable only from its own account), the Claude Code folder it was published from (when that is not the main one) and the local copy Flashex kept of it, readable whichever account is in use. An agent reads the local copy after an account switch instead of failing on the link. --json prints the API's answer as is.

zsh
❯ flashex artifacts

flashex artifacts add FILE [--title T] [--project P] [--json]

Keeps a local HTML, SVG or PDF page under Artifacts (local artifacts), with the stylesheets, scripts and pictures it names in its folder put inside its copy. --title names it (else the page's own title), --project gives its project by a Flashex project's name or a folder (else the project the file is in, else the folder it is added from). Added again after a change, it is a new version; unchanged, it says so. Pages Claude Code opens to show you (open page.html) and flashex browse page.html are kept this way by themselves. flashex artifacts lists them with local page: and the file they came from.

zsh
❯ flashex artifacts add docs/plans/accent-modes.html --project flashex
Kept under Artifacts: Accent modes (v1).

Naming a terminal: --surface or --to

Every --surface (and focus) takes a terminal's number (7 or #7) or its name, which is what you tell an agent: flashex send --to bubbles 'run the tests\n'. A name is the terminal's own (yours after Rename, on the Mac or the phone), the program's title, or what Claude Code calls the session running in it, in any case. Where two terminals share a name, project/name picks one (flashex/release), and the error lists them with their numbers. The start of a Claude Code session's id (at least 4 characters) works too.

flashex notify [--surface N] [--title T] [BODY]

A notification for a terminal: a highlighted frame, a dot on its tab and a count in the sidebar, and a system notification when you cannot see that terminal. Only a terminal takes one; without --surface it goes to the terminal the command runs in, else the one you used last. --from-claude-hook is what Claude Code's hooks run (see setup claude); a hook always exits 0, so Claude Code is never interrupted.

zsh
❯ make test; flashex notify --title Tests "finished with $?"

flashex agent [--surface N] <running|waiting|idle|error>

Sets the agent state shown in the sidebar, for agents without Claude Code's hooks.

zsh
❯ flashex agent waiting

flashex status [--surface N] [TEXT]

A status line for the terminal's project. Without text, the status is cleared.

flashex focus <SURFACE>

Shows a terminal: its project, tab and pane. The window comes to the front.

flashex send [--surface N] TEXT

Types text into a terminal. \n, \r, \t, \e and \\ are decoded, so flashex send 'ls\n' runs ls.

flashex read [--surface N | --caller] [--last-block | --scrollback N]

Prints a terminal's text:

  • no option: the visible screen;
  • --last-block: the output of the last finished command (needs shell integration); exits 1 when there is none or its output left the history;
  • --scrollback N: the last N lines up to the cursor's line, history included (at most 100 000). A wrapped line counts once.

Both read the shell's text also while a full-screen program shows its own. --caller reads the terminal the command runs in (it fails outside Flashex). Without --surface or --caller, it reads the terminal it runs in, or the focused one outside Flashex.

zsh
❯ cargo build; flashex read --last-block > build.log
❯ flashex read --surface 12 --scrollback 200 | grep -i error

flashex open [--project N | --surface N] PATH[:LINE[:COL]]

Opens a file in the editor, as ⌘-click does. If it is already open, its tab is shown; otherwise it opens in the tab's editor pane, or in a new split to the right. A relative path is resolved against the folder you run the command in. --project opens it in that project; --surface beside that terminal. A missing file or a folder is refused (exit 1), and nothing in the window moves.

zsh
❯ flashex open src/main.rs:120:8

flashex browse [--project N | --surface N] URL|FILE

Opens a web page in a browser panel: a new tab of the tab's browser pane, or a split beside the terminal. Any http:// or https:// address works; one without a scheme gets http://. A local HTML, SVG or PDF file opens too: ./index.html, ~/site/index.html, an absolute path, a file name in the current folder or a file:// address (a folder opens its index.html). Other schemes are refused. The new panel's id is printed. Without the browser panel (Linux), the page opens in the system browser.

zsh
❯ flashex browse localhost:3000

flashex events [--type T[,T…]] [--surface N]

Prints the app's events, one JSON object per line, until Ctrl+C. When stdout closes (| head -1) it exits 0; when the app closes the stream it exits 2. --type keeps only the named types; --surface only one terminal's events. At most 16 streams may be open at once.

typeFields
notificationsurface, title, body, bell (true for a BEL)
agentsurface, state (running, waiting, idle, error)
command-startedsurface, command, cwd (needs shell integration)
command-finishedsurface, command, cwd, exit_code, duration_ms
cwdsurface, cwd (the shell's folder changed)
focussurface (another terminal, editor or panel got the focus)
laggeddropped: this many events were lost because the reader was too slow

Events of one type and one terminal come in the order they happened; across types the order is only close, so compare by terminal and type.

zsh
❯ flashex events --type command-finished | while read -r ev; do echo "$ev" | jq .exit_code; done

flashex new-tab [--cwd DIR]

Opens a tab in the caller's project (in DIR if given) and prints the new terminal's id.

flashex split <right|down|left|up>

Splits the terminal and prints the new terminal's id.

zsh
❯ id=$(flashex split right) && flashex send --surface "$id" 'npm run dev\n'

flashex size [--surface N] [cols|rows] <N|N%>

Pins the size of the terminal's pane, as dragging its divider does: N columns or rows (1–2000), or N% (1–99) of its split. The size applies in the innermost split around the pane; cols or rows picks the nearest split in that direction. The pane keeps the size when the window is resized, until a divider is dragged or the split is equalized. Prints nothing.

zsh
❯ flashex size 60%          # the innermost split
❯ flashex size rows 12      # 12 rows high

flashex setup claude [--yes] [--print]

Adds Flashex's hooks to Claude Code's settings ($CLAUDE_CONFIG_DIR/settings.json, else ~/.claude/settings.json), so Flashex shows when Claude Code is working, waiting or done. It shows the change (a line diff of the hooks part) and asks first; --yes skips the question and --print only shows the change. Running it again is safe: older Flashex hooks are updated in place, missing ones added, current ones left alone, and your other hooks, keys and formatting stay. The old file is kept as settings.json.flashex-backup and, the first time, settings.json.flashex-backup.orig. A symlinked settings.json keeps its link; a read-only one is left alone.

zsh
❯ CLAUDE_CONFIG_DIR=~/.claude-work flashex setup claude

flashex keeper status [--json]

Lists the restart keepers (the helper that keeps terminals running across a crash, Restart Flashex or a quit) and what each holds: its process id, the Flashex version that started it, whether it is attached to a running app or holding terminals for the next one (and why), how many terminals it keeps and how many still run, how much output it has buffered and how long until they are stopped. It asks the keepers directly, so it works without a running app. It only looks.

zsh
❯ flashex keeper status
Restart keepers in /Users/me/Library/Application Support/flashex/keeper:
  keeper 4242 (Flashex 0.2.1): holding 3 terminals for the next app (Flashex was quit), 3 running, 1.2 KB buffered, stopped in 9 min 20 s unless Flashex is opened

flashex keeper stop [--json]

Ends the terminals a keeper holds while Flashex is closed, and that keeper, without opening the app. A keeper that belongs to a running Flashex is left alone, and the command says so. The exit code is 1 when a keeper did not stop.

zsh
❯ flashex keeper stop
Ended 3 terminals kept by keeper 4242 (3 running).

flashex todo list [--list NAME] [--json]

Prints a todo list: its categories and, under each, the items with their ids. Without --list it is the list of the project whose terminal the command runs in, else Inbox. The lists are Markdown files in todos in Flashex's data folder (~/Library/Application Support/flashex/todos/Inbox.md on macOS), which the command reads and writes itself: it works while Flashex is closed, and an open Todos window shows the change within seconds. --json prints the list, its file and the categories (the last one has "done": true).

zsh
❯ flashex todo list
flashex
To do (2)
  k3x9q2bd  Write the release notes
  p7m2w4zd  Try the Linux build
Done (1)
  h5t8c2nq  Fix the build

flashex todo add [--list NAME] [--to CATEGORY] TEXT

Adds an item at the end of the first category, or of the one named with --to (letter case does not matter). Prints the new item's id. A list that has no file yet is made with the categories from [todos] categories.

zsh
❯ flashex todo add --list Inbox Renew the certificate
w4k8n2xs  added to Inbox · To do

flashex todo move ID CATEGORY [--before ID]

Moves an item to the end of a category, or with --before ID before that item of the category: this is how items are put in order from a terminal (the category may be the one the item is in already). The first letters of an id are enough while only one item's id starts with them. The item is looked for in this terminal's list, then in the others; --list NAME looks only there. A category of several words needs no quotes. The lines under an item (notes, sub-points) move with it.

zsh
❯ flashex todo move k3x9 In progress
k3x9q2bd  moved to flashex · In progress
❯ flashex todo move k3x9 In progress --before p7m2
k3x9q2bd  moved to flashex · In progress, before p7m2w4zd

Flashex and the command take turns at a list's file (a lock on .<list>.lock beside it), so a change made in the window and one made here at the same moment are both kept.

flashex todo done ID

Moves an item to the list's last category, the one for what is finished.

flashex todo rm ID

Deletes an item.

flashex sync status [--json]

How Sync stands on this computer: its name, whether it is the main one or which one it syncs with, whether todo lists sync, and when each side last synced. It reads what Flashex last wrote, so it answers while Flashex is closed. --json prints the same as an object (name, role: main, client or alone, todos, hub with state: ok, offline, error or never, and devices).

zsh
❯ flashex sync status
MacBook Pro: syncs with Mac mini
Todos: sync
Mac mini (https://mini.tailnet.ts.net:8443): in sync, synced 2 min ago

flashex sync now

Asks the running Flashex to sync with the main Mac at once and waits for how it went (exit code 1 when the main Mac is offline or refuses). On the main Mac there is nothing to do: the others sync with it.

flashex vault list, get, run, env, import

Secrets from the Vault (command palette › Vault…). flashex vault list [--json] prints the entry names, never values. flashex vault get [-n] [--print] NAME prints an entry's main secret (an API key's value, a login's password, an SSH key's private key) into a pipe or a file; to a terminal only with --print. flashex vault run VARS… -- COMMAND [ARGS…] runs a command with values in its environment. flashex vault env [--format dotenv] [--print] [--out FILE [--force]] VARS… prints KEY=VALUE lines into a pipe or a file (> .env.local); to a terminal only with --print; --out FILE writes a file only you can read. flashex vault import --set NAME [--replace] [FILE|-] saves a .env file (or standard input) as the set NAME (dev, stage, prod) of the terminal's project: entries NAME/VAR tagged NAME; --replace changes values that are there already.

In a Flashex terminal a name is looked up among its project's entries first, then among the global ones; another project's entries are never reached. --project looks only among the project's, --global only among the global ones.

VARS, any number and mixed: --env VAR=ENTRY puts the entry in $VAR; --env ENTRY or --entry ENTRY puts it under its own variable name (the Variable you set on an API key, such as OPENAI_API_KEY, else the entry's name); --all-tagged TAG puts in every entry with that tag that has a variable name; --set NAME puts in a set saved with vault import.

For get, run and env Flashex brings its window forward and asks: which entries and which variables they go into, which process (its name, pid and program, and its parent's, as the system reports them), and what the command says about itself (its terminal, the command it will run, and with env --print that it prints the values on the terminal: shown as claims). Nothing is sent until you press Allow. A locked vault is unlocked in the same card first; list waits only for that. The command waits up to 90 seconds; Deny, no answer, or too many requests waiting ends it with exit code 1.

Careful with values on screen. A value printed in a terminal stays in its scrollback, which flashex read returns without asking and which survives a restart. Prefer vault run, a pipe (flashex vault get GH_TOKEN | pbcopy) or Copy in the Vault. Flashex checks only where flashex itself writes: | tee, | cat or vault run -- printenv still put values on the screen after you allow them. Values in a command's environment can be read by other programs running as your user while it runs.

zsh
❯ flashex vault run --env OPENAI_API_KEY -- python agent.py
❯ flashex vault run --all-tagged ci -- make deploy
❯ flashex vault env --entry openai --entry anthropic > .env.local
❯ flashex vault import --set stage .env.stage
❯ flashex vault run --set stage -- npm run deploy

flashex --version, flashex --help

Print the version, or the usage of every command.

The socket API

Programs that can write to a Unix socket can use the same API directly: JSON-RPC 2.0, one message per line.

request
{"jsonrpc":"2.0","id":1,"method":"read","params":{"surface":3,"last_block":true}}

Every answer is one line too: {"jsonrpc":"2.0","id":1,"result":{…}} or an error with a code and message. A request without an id is carried out but not answered. A request may be at most 1 MiB; an idle connection closes after 120 s; at most 64 connections may be open. surface is optional wherever it appears; the default is the focused terminal. to (a terminal's name) may stand in its place.
